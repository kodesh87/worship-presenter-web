## Intent

**Problem:** Every bundled background in `public/assets/` is a screenshot of a *finished slide* with text baked into the pixels, and `transform-registry-v1.mjs`'s hardcoded `ASSET_MAP` assumed `slides-new/slide-NN.jpg` matched deck slide NN — it does not, because that folder holds 57 renders of a 60-slide deck, so the mapping drifts by one then two. Sixteen of seventeen assets therefore show the wrong slide entirely: `prayer-bg.jpg` (used behind Opening Prayer, Closing Prayer and Intercessory Prayer) is a picture of the *Opening Song* slide, `choir-bg.jpg` (behind both song cues) is a picture of a *song title* slide reading "SDAH #469 — Leaning on the Everlasting Arms", and `announcements-bg.jpg` / `fellowship-bg.jpg` / `midweek-bg.jpg` are one byte-identical file. Separately, a text element whose content needs more room than its declared box simply overflows and paints across its neighbours.

**Approach:** Extract the original picture parts straight out of the source deck's `ppt/media/`, which are clean plates with no text, and rebuild `public/assets/` plus the seed's `backgroundImage` references from a generated slide→media table rather than a hand-written one. Separately, make an over-long text element shrink to fit its box in both renderers instead of spilling out of it.

## Boundaries & Constraints

**Always:**
- Backgrounds come from `260704 - BIC Worship Presentation.pptx` by reading `ppt/slides/slideN.xml` + its `.rels` and copying the referenced blob out of `ppt/media/` **byte-for-byte**. No rendering, no re-encoding, no upscaling — the deck's own pictures are the fidelity ceiling and the source of truth.
- The mapping from template to slide to media file is generated by a script and committed as data, so the drift that caused this defect cannot silently return.
- Every `backgroundImage` in `data/default-registry.json` must resolve to a committed file under `public/assets/`, and must pass `isRegistryImageRef`.
- Asset filenames describe the template that uses them, not the picture's subject, so a future mismatch is visible in review.
- Where two templates legitimately share one source picture (Prayer Partners and Opening Prayer both use the same plate; both song cues share another), they reference the same committed file — one copy, two references.
- Element geometry, text content, font sizes, colours and layout keys stay exactly as they are. This change touches `backgroundImage` values and the bytes behind them, nothing else in the seed.
- Text that does not fit its element box shrinks to fit rather than overflowing. Nothing may paint outside its own element box in either renderer.
- Registry writes stay admin-only and validated; the seed keeps its missing-only insert semantics.
- New tests use `node:test` and are appended to the explicit `package.json` test list.
- Read the relevant guide under `node_modules/next/dist/docs/` before touching Next.js APIs.

**Block If:**
- A template's source slide cannot be identified from the deck with confidence. Do not guess a plate — leave that template on a solid `backgroundColor` and report it.

**Never:**
- Do not use `slides/`, `slides-new/` or `slides-all/` as a source. All three are finished-slide screenshots with text baked in; they are what caused this.
- Do not extract the `.mp4` media — video is an explicit SPEC non-goal.
- No change to slide order, hymn splitting, placeholder resolution, or the artifact runtime contract.
- Do not re-encode, resize, sharpen or "improve" a picture. If a plate looks soft, that is the deck's own resolution.
- Do not silently drop a background to dodge a hard mapping — that is the Block If.

## Spec Change Log

### 2026-07-26 - Implementation finding

**Triggering finding:** while calibrating shrink-to-fit, the implementer reported that every `style.fontSize` in the registry is 1.5x too large, and I verified it directly against the deck. The source slide is `18288000 x 10287000` EMU = 20 x 11.25 in = 1440 x 810 **pt**. PowerPoint stores `sz="15263"` = 152.63 **pt**. `scripts/extract-pptx-layout.mjs` wrote that number straight into `style.fontSize`, which `registry-contract.md` defines as **px on a 960x540 reference canvas**. The correct value is `152.63 * (540/810) = 101.75`. Geometry was converted correctly; only the font unit was not.

**Amended:** the Always rule freezing font sizes is narrowed - geometry, text content, colours and layout keys still stay exactly as they are, but the 56 `style.fontSize` values are divided by 1.5 to convert point sizes into reference pixels. A task was added for it.

**Known-bad state avoided:** shipping shrink-to-fit as a permanent 0.67x correction for a unit bug. The masking was already visible in the data - single-line elements were measuring a fit scale of almost exactly 1/1.5, which is the signature of the bug rather than of genuinely over-full boxes. Left unfixed, every slide would have rendered typography 50% larger than the deck the user asked to reproduce exactly, and the compensation would have been invisible in the registry.

**Contract impact:** none to the `<intent-contract>`. Its intent is fidelity to the source deck; freezing an incorrect font size worked against that intent rather than for it.

**KEEP:** the shrink-to-fit policy itself, which stays as the safety net it should always have been - CSS line-height 1.2 still exceeds PowerPoint's `spAutoFit` hug by a little, so a few elements shrink slightly. Also keep the implementer's two rejections, both of which were right: `sermon-flyer` must not ship one week's flyer artwork as a default background, and the four templates that were wrongly sharing a plate now have their own.


## Review Triage Log

## Design Notes

The defect is a mapping bug, not a rendering bug, and the fix has to remove the class of error rather than the instance. `transform-registry-v1.mjs` mapped by *position* — `slides-new/slide-04.jpg` was assumed to be deck slide 4 — against a folder that was missing three slides. Every downstream name was therefore a plausible-looking lie. Generating `data/asset-map.json` from the deck itself, with the slide's own text runs recorded as evidence, means a wrong mapping is visible in the diff instead of only on a projector.

Native resolution is the ceiling and it is lower than what is committed today:

```
deck plate   1672 x 941   (what PowerPoint itself displays, upscaled ~1.15x on a 1920x1080 slide)
committed    2880 x 1620  (a 1.72x upscale of a screenshot — interpolation, no real detail)
```

So the rebuilt assets are both correct and smaller. That also helps the generated deck, which is already ~10 MB.

Three templates have no honest plate: `family-youth` (the source slide is photos on a solid fill), `contact` (its picture covers only part of the slide) and `announcements-header` (no source slide exists — it was hand-added during the v1 transform). Each keeps its solid `backgroundColor`. Inventing a background for them would be the same mistake in a new coat.
