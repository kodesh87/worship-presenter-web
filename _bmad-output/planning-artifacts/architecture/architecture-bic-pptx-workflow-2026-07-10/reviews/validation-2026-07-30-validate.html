High H1 · A fresh install can seed vocabulary the migration will never see (boot-order hole)

Today's shipped data/default-registry.json still reads "baseType": "text-placeholder". Separately, AD-21's future migration reasons that a brand-new database starts at data version 1, so its one-time migration is a no-op there by design. Neither AD fixes boot order: getDb() runs schema DDL → migration/backfill → seedArtifactRegistry last. If the future migration keeps that order, a fresh install migrates an empty table, stamps the version at head, and only afterward inserts seed rows straight from the still-unconverted JSON — rows the migration will never touch again.

Fix: an explicit clause that the seed file is authored in the vocabulary of the current production data version, asserted by a test — or reorder to seed-then-migrate.

High H3 · Where a SongSet slot identity lives is a fork handed to two owners, and it breaks silently

The spine's own Deferred section already names this fork and declines to close it: whether the four slot identities live in base_type itself or in a discriminator column beside it.
